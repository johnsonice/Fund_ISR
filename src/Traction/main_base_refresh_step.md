# Main-base refresh workflow

This note is for agent reference when **refreshing the main-pipeline base**
(the canonical set of inference + final-dataset outputs in
`/data/home/xiong/data/Fund/CSR/Tractions/output/main_base/`) so that
subsequent incremental runs can merge against it instead of the frozen
archive at `/data/home/xiong/data/Fund/CSR/Traction-archieve/output/`.

All main-base inputs and outputs live under the `main_base/` subdirectory of
`output/` to keep them isolated from in-flight experimental files. Override
with `MAIN_BASE_DIR=/path/to/elsewhere` on any of the scripts below if
needed.

The companion runbook for processing newly arrived XML is
[incremental_update/incremental_update_step.md](incremental_update/incremental_update_step.md).

## Scope

What this workflow **does** rerun:
- 4 fine-tuned per-sector inference jobs (monetary/fiscal × agreement/stance).
- 1 zero-shot general (cross-sector) agreement job.
- The final-dataset build (`df_fin.csv` + `df_fin_reg_core.csv`).

What it does **not** rerun (these are reused from existing
`/output/main_base/`):
- XML extraction → `df_aiv.csv`, `df_paragraphs.csv`.
- Topic classification → `paragraph_with_sector_batch.csv`,
  `document_by_type_sector.csv`.

If those upstream artifacts are missing or stale, regenerate them through the
main pipeline (`data_preprocess.py` → `topic_identification_batch.py` →
`paragraph_back2_doc.py`) **before** running this workflow.

## Inputs required in `/output/main_base/`

- `df_aiv.csv` — document-level metadata with `paragraphs_*` columns,
  `staff_verified`, `Print ISBN`, `Year from title`, `Primary Country Code`,
  `Publication Date`, `has_buff`. (`Primary Country Description` is optional
  for the main `df_aiv.csv`; the shared module falls back to the country
  name from `docs/reference/country_meta_info.xlsx` when it's absent.)
- `document_by_type_sector.csv` — long-form per-document-per-topic table with
  `Print ISBN`, `type` (`staff`/`buff`), `topic`, `text`, `country`, `year`.

## Outputs written to `/output/main_base/`

- `df_documents.csv` — per-document staff/buff/country/year rollup.
  **Copied from the archive** (`Traction-archieve/output/df_documents.csv`);
  not regenerated by the adhoc helper.
- `agreement_monetary_results.csv`, `agreement_fiscal_results.csv` —
  fine-tuned agreement classifications + `disagreement_areas`.
- `stance_monetary_results.csv`, `stance_fiscal_results.csv` —
  fine-tuned stance classifications (long format, per author per topic).
- `df_documents_general.csv` — zero-shot per-sector agreement scores
  (`Agreement_General` + `Agreement_{Monetary,Fiscal,External,Financial,Real}`,
  -5..5, with 99 = insufficient info).
- `df_fin.csv` — full document-level analysis dataset, includes text columns
  and `policy_mix_staff`/`policy_mix_buff`.
- `df_fin_reg_core.csv` — core subset matching the archive schema (the file
  `incremental_update/08_merge_all_incremental.py` merges incremental rows
  into).

## Scripts and call graph

```
scripts/inference/run_main_base_refresh.sh        ← entry point
├─ scripts/inference/run_all.sh                   (4 per-task inference, in parallel)
│   ├─ scripts/inference/run_monetary_agreement.sh   → ft:gpt-4.1 monetary-agreement
│   ├─ scripts/inference/run_fiscal_agreement.sh     → ft:gpt-4.1 fiscal-agreement
│   ├─ scripts/inference/run_monetary_stance.sh      → ft:gpt-4.1 monetary-stance
│   └─ scripts/inference/run_fiscal_stance.sh        → ft:gpt-4.1 fiscal-stance
├─ scripts/inference/run_general_agreement.sh     (cp df_documents.csv from archive, then zero-shot)
│   └─ inference_general_agreement.py
└─ scripts/inference/run_create_final_dataset.sh  (after both groups complete)
    └─ create_final_dataset.py
        └─ post_estimate_analysis/final_dataset_utils.py::build_final_dataset
```

All four per-task `run_{domain}_{task}.sh` scripts pass `--data-file
${MAIN_BASE_DIR}/document_by_type_sector.csv` and `--output-dir
${MAIN_BASE_DIR}` explicitly, where `MAIN_BASE_DIR` defaults to
`/output/main_base/`. Override the env var to retarget. The python defaults
in `inference_agreement_stance.py` still point at the bare `/output/` dir
and are no longer used by the main-base workflow.

`run_main_base_refresh.sh` runs `run_all.sh` and `run_general_agreement.sh`
**in parallel** (independent inputs: `document_by_type_sector.csv` vs
`df_documents.csv`), then waits for both before invoking
`run_create_final_dataset.sh`.

The shared transformation lives in
[post_estimate_analysis/final_dataset_utils.py](post_estimate_analysis/final_dataset_utils.py).
Both the main-pipeline builder
([create_final_dataset.py](create_final_dataset.py)) and the incremental
builder
([incremental_update/07b_create_final_dataset_incremental.py](incremental_update/07b_create_final_dataset_incremental.py))
call `build_final_dataset()` from that module — keep it as the only place
where final-dataset logic changes are made.

## How to run

### Option A — one shot

```bash
bash src/Traction/scripts/inference/run_main_base_refresh.sh
```

This kicks off the 4 per-task jobs and the general-agreement job in parallel,
waits for everything, and builds `df_fin.csv` + `df_fin_reg_core.csv`.

### Option B — step by step

```bash
# Stage 1a: 4 fine-tuned per-task inference jobs (parallel)
bash src/Traction/scripts/inference/run_all.sh

# Stage 1b: zero-shot general agreement (copies df_documents.csv from archive first)
bash src/Traction/scripts/inference/run_general_agreement.sh

# Stage 2 (after 1a and 1b complete): build final dataset
bash src/Traction/scripts/inference/run_create_final_dataset.sh
# equivalent: python src/Traction/create_final_dataset.py
```

CLI options on the final-dataset builder:

```bash
python src/Traction/create_final_dataset.py --start-year 2015 --end-year 2023
# --source-dir defaults to config.output_dir / "main_base"
```

### Before launching full batches
1. **Confirm `df_documents.csv` is in place**:
   `ls -la /data/home/xiong/data/Fund/CSR/Tractions/output/main_base/df_documents.csv`
   should report ~50.7 MB. If absent, `run_general_agreement.sh` copies it
   from the archive on first run.
2. **Smoke-test each fine-tuned job** with `--test-mode --sample-size 50`
   before scaling up. Inspect `agreement_*_results.csv` and
   `stance_*_results.csv` for hallucinated values in `agreement` /
   `stance_current` / `stance_future` / `stance_near_term`. The shared
   module's `_clean_nan_str` and the inline cleaner in
   `build_final_dataset` handle the historical hallucinations
   (`"Micah mostly agree"`, `"appropriately agree"`, `"валлийский"`); new
   variants need to be added if they appear.
3. **Regression check on 07b**: run the refactored incremental 07b against
   the existing `output/incremental_update/05252026_update/` directory and
   diff `df_fin_core_incremental.csv` against the pre-refactor snapshot
   (sort by `Print ISBN` first). Expected: identical core schema and values.
   The full `df_fin_incremental.csv` now also has `policy_mix_*` columns.

### After the full rerun
4. Verify `/output/main_base/` contains:
   - `agreement_{monetary,fiscal}_results.csv`,
     `stance_{monetary,fiscal}_results.csv`
   - `df_documents.csv` (copied from archive)
   - `df_documents_general.csv` (zero-shot)
   - `df_fin.csv` (59 cols incl. `policy_mix_*`; will grow if upstream
     adds new columns)
   - `df_fin_reg_core.csv` (matches archive's 44-col core schema —
     see `final_dataset_utils.CORE_COLUMNS`)
5. Row-count sanity: on the 2015–2023 window, `df_fin_reg_core.csv` should
   match the archive **exactly** (981 rows, verified). Anything outside
   that window (e.g. 2024) is additional, not a discrepancy. The full
   dataset row count for the most recent run was 1019 (981 + 38 from
   2024).
6. **Merge incremental against the fresh base**:
   ```bash
   python src/Traction/incremental_update/08_merge_all_incremental.py
   # --main-dir defaults to /output/main_base; pass it explicitly to point at
   # a different base (e.g. the frozen Traction-archieve/output).
   ```
   Expect `df_fin_reg_core_merged.csv` to grow by the new incremental row
   count (deduped by `Print ISBN`), and per-pair stats in stdout should
   report `skipped_already_in_main` ≈ overlap.
7. **Visualization regression**: open
   `post_estimate_analysis/data_vis_v4.ipynb`; the `policy_mix_*` cells
   should consume `/output/main_base/df_fin.csv` and produce the same plots

## Stop conditions

Surface the issue before continuing if any of the following happens:

- A per-task batch job fails or returns < 90% successful structured outputs.
- The 4 per-task CSVs' `agreement` / `stance_*` columns contain values
  outside the schema enums (signals model drift or a stale prompt).
- `df_documents.csv` is missing from the archive (the `cp -n` step in
  `run_general_agreement.sh` will silently no-op an absent source; check
  the script's stdout).
- `build_final_dataset` warns about missing `CORE_COLUMNS` — the full
  output dropped a column the core schema expects, usually a sign the
  upstream inference output is missing rows.
- Post-rerun `df_fin_reg_core.csv` row count is materially different from
  the archive's (>5% drift on the same 2015–2023 window).

## Known gotchas

Things that have bitten previous runs — left here so the next agent doesn't
rediscover them.

- **Conda activation silently no-ops in background contexts.** All
  `run_*.sh` scripts pin `TRACTION_PY=/data/home/xiong/miniconda3/envs/traction/bin/python`
  explicitly. If a script reverts to a bare `python` call, you'll see
  `ModuleNotFoundError: No module named 'frontmatter'` because the wrong
  interpreter runs. Don't "fix" by installing into the wrong env — restore
  the explicit `TRACTION_PY` invocation.
- **Main `df_aiv.csv` schema differs from incremental.** The main
  `df_aiv.csv` (produced by `data_preprocess.py`) lacks
  `Primary Country Description`; the incremental step 02 adds it. The
  shared module ([final_dataset_utils.py](post_estimate_analysis/final_dataset_utils.py))
  handles this by falling back to `country_meta_info.xlsx`'s `Country`
  column (joined on ISO3). Don't `KeyError`-fail if the column is missing.
- **The 44-col `CORE_COLUMNS` schema is load-bearing.** Step 08 merges
  `df_fin_core_incremental.csv` into archive `df_fin_reg_core.csv` by
  concatenation, so both sides must share the column set. If you add a
  column to `CORE_COLUMNS`, regenerate both the archive's core file and
  the main-base core file before next merge — otherwise concat will
  produce ragged columns.
- **`policy_mix_staff` / `policy_mix_buff` belong in the full output, not
  core.** Adding them to `CORE_COLUMNS` would break the merge (see above).
  `data_vis_v4.ipynb` reads them from `df_fin.csv` (full), not the core
  CSV.
- **`bm_date` is intentionally NaN.** It's a placeholder column kept for
  schema parity with the archive. Don't try to populate it during the
  rerun.
- **`df_documents.csv` is copied verbatim from the archive.** The adhoc
  helper `incremental_update/adhoc/generate_df_documents_from_aiv.py` is
  NOT used for the main base — it produced a different (and incomplete)
  schema than the archive's original file. If the archive's file changes,
  copy the new one over.

## Agent operating rule

1. Confirm the upstream files (`df_aiv.csv`, `document_by_type_sector.csv`)
   are present and recent enough. Do not silently rerun XML extraction or
   topic classification.
2. Smoke-test (`--test-mode`) one job to validate the path / env before
   firing the full batch.
3. Run `run_main_base_refresh.sh` (or the three sub-stages manually).
4. Verify outputs against the checks above.
5. Only then suggest the merge invocation against the fresh base.
